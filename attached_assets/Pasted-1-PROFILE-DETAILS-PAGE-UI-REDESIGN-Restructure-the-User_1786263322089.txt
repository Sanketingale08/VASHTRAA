2. EDIT MOBILE NUMBER BUTTON
==================================================

Add a dedicated "Edit" button next to the Mobile Number.

Example:

Mobile Number     9561573308     [Edit]

Open a secure modal/dialog.

Step 1:

Show:

Current Mobile Number:
XXXXXX3308

New Mobile Number:
[ +91 __________ ]

[Send OTP]

The new mobile number must be validated before sending OTP.

Validation:
- Accept valid Indian mobile numbers.
- Use +91 where required.
- Reject invalid numbers.
- Prevent empty input.
- Prevent obviously invalid formats.
- Do not expose sensitive information.

After clicking "Send OTP":

Send OTP to the NEW mobile number.

Display:

OTP Verification

We have sent a verification OTP to:
+91 XXXXX XXXXX

Enter OTP:
[ _ _ _ _ _ _ ]

[Verify OTP]

Also provide:

Resend OTP

with an appropriate cooldown timer.

IMPORTANT SECURITY REQUIREMENT:

The OTP must be sent to the NEW mobile number, not the old mobile number.

The mobile number must NOT be updated in the database until OTP verification succeeds.

Only after successful OTP verification:

1. Verify OTP on the backend.
2. Validate that the OTP is valid and has not expired.
3. Update the user's mobile number in the database.
4. Update the authenticated user's profile state.
5. Refresh the profile UI immediately.
6. Show a success message:

"Mobile number updated successfully."

If OTP verification fails:

"Invalid or expired OTP. Please try again."

Do NOT update the database before successful OTP verification.

6. MOBILE + EMAIL VERIFICATION LOGIC
==================================================

IMPORTANT ARCHITECTURE REQUIREMENT:

Do NOT handle OTP verification only on the frontend.

OTP generation, storage, expiry, verification, and update operations must be handled securely on the backend.

Implement:

Generate OTP
↓
Store hashed OTP or secure OTP representation
↓
Set expiry time
↓
Send OTP
↓
User enters OTP
↓
Backend verifies OTP
↓
If valid:
    Update database
    Update session/profile
↓
Return success response

OTP requirements:

- 6-digit OTP
- Short expiration period
- One-time use
- Rate-limit OTP requests
- Rate-limit verification attempts
- Prevent OTP reuse
- Invalidate previous OTP when a new OTP is generated
- Never log OTP values in production logs
- Never expose OTP in frontend responses
- Never store plain-text OTP if the existing architecture supports secure hashing

12. SECURITY
==================================================

Ensure:

- OTP verification happens server-side.
- User can only update their own profile.
- Backend validates authenticated user ID/session.
- OTP cannot be reused.
- OTP expires.
- OTP requests are rate-limited.
- Verification attempts are rate-limited.
- Do not expose OTP through API response.
- Do not expose sensitive database information.
- Validate all user inputs server-side.
- Prevent unauthorized profile updates.
- Prevent changing another user's email/mobile through manipulated API requests.
