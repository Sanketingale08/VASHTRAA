Implement Saved Cards & Saved UPI – User/Customer Portal
The User Portal / Customer Portal already exists and is working.

DO NOT:
* Remove any existing functionality.
* Change the existing authentication/RBAC architecture unless required for this feature.
* Break existing payment, checkout, profile, cart, or order functionality.

Only implement the Saved Payment Methods functionality on the **User/Customer side.

---

# PROJECT GOAL

Implement a secure **Saved Payment Methods feature for customers in customer dashboard.

Customers should be able to:

1. Save a debit/credit card.
2. Save a UPI ID.
3. View their saved cards.
4. View their saved UPI IDs.
5. Set a default payment method.
6. Delete a saved payment method.
7. Use a saved payment method during checkout.

The feature must be associated with the currently authenticated customer.

# 3. ADD CARD

Provide an **Add Card** button.

The form should contain:

* Cardholder Name
* Card Number
* Expiry Month
* Expiry Year
* CVV
* "Set as default" checkbox

Validation:

* Card number must be valid.
* Expiry date must not be expired.
* CVV must have the correct format.
* Cardholder name is required.
* Prevent duplicate cards where possible.
* Show clear validation/error messages.

IMPORTANT:

## SECURITY

DO NOT store raw:

* Card number
* CVV
* Full payment credentials

in the application's database.

If the application uses a payment provider such as Stripe/Razorpay/etc. use the provider's secure tokenization/payment-method mechanism.

Store only safe information such as:

```text
paymentProvider
paymentMethodId / token
cardBrand
last4
expiryMonth
expiryYear
cardholderName
isDefault
createdAt
```

CVV must NEVER be stored in the database.

If a payment gateway is already integrated into the project, reuse the existing integration instead of creating another payment system.

Form:

```text

[________________]

[Save UPI]
```

Validation:

* UPI ID is required.
* Validate standard UPI format such as:

```text
username@bank
```

Examples:

```text
name@oksbi
name@paytm
name@ybl
name@upi
```

Do not allow obviously invalid UPI IDs.

If the existing payment gateway supports UPI verification/tokenization, use the existing gateway integration.

Do not store unnecessary sensitive payment information.

# 9. DEFAULT PAYMENT METHOD

A customer can have one default payment method.

When the user selects:

```text
Set as default
```

the backend should:

1. Find the user's existing default payment method.
2. Set it to `isDefault = false`.
3. Set the selected payment method to `isDefault = true`.

Example:

```text
Card A → false
Card B → true
UPI C  → false
```

Only one payment method should be default.

If the user saves their first payment method, automatically make it the default.

---

# 10. DELETE PAYMENT METHOD

When the user clicks **Delete**:

Show a confirmation:

```text
Are you sure you want to remove this payment method?
```

After confirmation:

* Delete/deactivate the payment method.
* Refresh the payment-method list.
* Show a success message.

If the deleted method was the default:

* Automatically select another saved method as default if one exists.
* Otherwise, leave the user with no default payment method.

# 12. BACKEND SECURITY

Implement proper validation and authorization.

Requirements:

* Authentication required for every payment-method API.
* Validate all request bodies server-side.
* Never trust frontend validation alone.
* Never store CVV.
* Never store full card numbers unless the existing payment provider explicitly requires a secure tokenized mechanism—and preferably use provider tokens instead.
* Do not expose payment-provider secrets to the frontend.
* Use environment variables for payment gateway keys.
* Prevent IDOR/access-control vulnerabilities.
* Sanitize/validate UPI and card-related input.
* Return only safe payment-method information to the frontend.
