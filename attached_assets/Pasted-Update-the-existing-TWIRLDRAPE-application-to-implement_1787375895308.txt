Update the existing TWIRLDRAPE application to implement automatic Vendor ID generation using the existing database.

First, carefully inspect the existing Seller/Vendor registration flow, Vendor ID implementation, Admin Vendor Management, database structure, authentication, approval workflow, and APIs.

Do not break or remove any existing functionality. Do not unnecessarily change the existing UI, APIs, authentication, payment, shipping, or database structure.

### Objective

The Vendor ID must be generated automatically by the server/database when an Admin approves a seller.

The Seller must never manually enter or generate a Vendor ID.

Use the following Vendor ID format:

TDV000001
TDV000002
TDV000003
TDV000004
...

Where:

* TD = TWIRLDRAPE
* V = Vendor
* The numeric portion is a unique sequential number.

### Required Workflow

Seller Registration
↓
Seller Account = Pending
↓
Admin reviews seller
↓
Admin clicks "Approve Seller"
↓
Server generates the next available Vendor ID
↓
Vendor ID is saved in the database
↓
Seller status = Approved
↓
The same Vendor ID is displayed on both Admin and Seller panels

### Database Requirements

Use the existing database and database connection.

Do not create a separate external service or third-party API for Vendor ID generation.

Implement a reliable database-backed sequence/counter mechanism.

The Vendor ID must:

* Be unique
* Never be duplicated
* Be generated server-side
* Not depend on frontend input
* Not be editable by the seller
* Not be manually typed by the Admin
* Remain permanently associated with the approved seller

Add a unique database constraint/index for the Vendor ID if one does not already exist.

Make sure concurrent seller approvals cannot generate the same Vendor ID.

For example, if two sellers are approved at the same time:

Seller A → TDV000001
Seller B → TDV000002

Never allow both sellers to receive the same Vendor ID.

### Admin Panel

Update the existing Admin Vendor Management section so that Admin can:

1. View pending sellers.
2. Open seller details.
3. Approve the seller.
4. Automatically trigger Vendor ID generation during approval.
5. See the generated Vendor ID after approval.

Do not add a manual Vendor ID input field.

For pending sellers, show:

Vendor ID: Not Generated

After approval:

Vendor ID: TDV000001

The Admin should not have to type or manually generate the ID.

### Seller Panel

Keep the existing Vendor ID display on the Seller side.

After Admin approval, automatically show the Vendor ID generated by the server.

Example:

Vendor ID: TDV000001

The seller must only be able to view the Vendor ID, not edit it.

### Existing Vendor IDs

Before implementing the new logic, inspect the database for existing sellers/vendors that already have Vendor IDs.

Do not overwrite existing valid Vendor IDs.

Do not regenerate Vendor IDs for already approved sellers.

Continue the sequence from the highest existing Vendor ID.

For example, if the database already contains:

TDV000001
TDV000002
TDV000003

the next approved seller must receive:

TDV000004

### Approval and ID Generation

Vendor ID generation and seller approval should be handled safely on the server.

The system should not:

1. Approve the seller first and generate the ID later.
2. Generate the ID in the browser.
3. Accept a Vendor ID from the frontend request.
4. Allow the seller to modify the Vendor ID.
5. Generate duplicate IDs.

Ideally, approval and Vendor ID assignment should happen as one reliable database operation/transaction where supported.

### Error Handling

If Vendor ID generation fails:

* Do not incorrectly mark the seller as fully approved.
* Show a clear error message to the Admin.
* Log the server-side error.
* Allow the Admin to retry the approval.
* Do not create duplicate Vendor IDs during retry.

If the seller is already approved and already has a Vendor ID, do not generate another ID.

### Security

The Vendor ID generation must only be triggered through the authorized Admin approval workflow.

Do not trust any Vendor ID received from the frontend.

The server must determine the Vendor ID.

Verify that only authorized Admin users can approve sellers.

### Important

Before making changes, inspect the existing implementation and reuse the existing:

* Seller/Vendor model
* Database connection
* Admin approval API
* Seller approval workflow
* Authentication/authorization
* Existing Vendor ID fields
* Existing Admin Vendor Management UI

Do not create duplicate models, duplicate APIs, or duplicate Vendor ID systems if they already exist.

### Testing

After implementation, test the following scenarios:

1. Approve the first pending seller → TDV000001.
2. Approve the second seller → TDV000002.
3. Approve multiple sellers → sequential unique IDs.
4. Approve two sellers concurrently → no duplicate IDs.
5. Retry approval after an error → no duplicate ID.
6. Refresh Admin panel → Vendor ID remains unchanged.
7. Refresh Seller panel → same Vendor ID is displayed.
8. Seller attempts to modify Vendor ID → modification is rejected.
9. Existing Vendor IDs remain unchanged.
10. Next generated ID continues correctly from the highest existing Vendor ID.
11. Already approved seller does not receive a new Vendor ID.
12. Unauthorized user cannot trigger Vendor ID generation.
